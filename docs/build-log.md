| 2026-09-03 | The allocator's candidate scoring (`pipeline/allocator.py`) doesn't depend on `attempts_used` - it's always the same 3 safe-spacing offsets computed from the original failure time. That meant a second retry attempt for the same payment re-selected the identical highest-scoring window the first attempt had already tried and failed at, instead of moving to the next-best one. | The Sec 5.2 sensitivity sweep (`eval/sensitivity.py`) surfaced it, not a unit test: at `funding_event_day=1.5` (an early funding event), the allocator's recovery count was worse than the naive fixed-schedule baseline in 9/9 of those grid points. Baseline's day1/day2/day3 spread genuinely probes 3 different times, so it was outperforming an allocator that was effectively retrying at the same instant 3 times. | Changed `allocate()` to rank all compliant candidates by score descending and index into the ranking with `attempts_used` (attempt 1 gets the best window, attempt 2 the next-best, etc.) instead of always taking the single top-scored one. Added `test_successive_attempts_pick_distinct_windows_not_the_same_one_again` and `test_attempt_order_follows_descending_score` as regression coverage, then re-ran the full batch and sweep. Afterward the recovery-count advantage over baseline held at only 6/27 sweep points, down from a buggy 17/27 - all 6 were exactly `funding_event_day=5.0`, a late funding event baseline's tight day1/2/3 schedule structurally can't reach while the allocator's wider PRD-mandated 24h/72h/7d schedule can. Left the offset weights and the safe-spacing offsets alone rather than retuning either to chase a better number - both are PRD-specified (Sec 2's published spacing) or a declared, independently-authored heuristic, and CLAUDE.md is explicit that changing either in reaction to a less flattering result is the outcome-model-gaming pattern to avoid. Wrote up docs/RESULTS.md accordingly: attempts-spent efficiency and zero-waste-on-unrecoverable-causes hold at every grid point, raw recovery count only wins when funding timing is late, and that's precisely the gap Stage 4 funding-window inference (build step 9) exists to close. |
| 2026-09-03 | Wired real funding-window inference (`pipeline/funding_window.py`, Stage 4) into the allocator, expecting it to meaningfully close the early/mid-funding-event gap the sensitivity sweep exposed the day before. It barely moved the numbers: allocator attempts spent 77 to 74, recovered 31 to 30, sweep advantage holding at 6/27 to 7/27 grid points. | Ran the full batch and sweep before and after wiring it in and diffed the results, per the build plan's own instruction to "diff against step 7's numbers... if funding-aware timing doesn't move the needle, say so." | Two structural reasons, not a bug in either. The allocator's candidate set is still only the 3 fixed safe-spacing offsets (24h/72h/7d, PRD Sec 2's own published spacing), so a funding-window estimate can only re-rank which of those 3 gets tried first - it can't place a retry at the actually-inferred day if that falls between offsets. Separately, `eval/outcome_model.py` (frozen before this stage was built, Sec 5.1) is population-level rather than per-customer, so even a perfect estimate wouldn't change the underlying success probability the simulation draws from. Left the frozen outcome model untouched and didn't add a 4th candidate offset to manufacture a better number - both would have been scope changes made in reaction to a disappointing result, which is what the outcome-model-isolation rule exists to prevent. Documented as a limitation instead: funding-window inference is built, tested, and wired in, but its ceiling in this architecture is reordering fixed offsets, not free-form scheduling. |

| 2026-09-03 | `eval/batch_generator.py`'s `generate_batch` anchored synthesized failure times to `datetime.now(IST)` instead of a fixed reference point, despite the module claiming to be seeded for reproducibility. Re-running the sensitivity sweep with the identical seed and n produced a different result - advantage held at 7/27 grid points, then 6/27 an hour later. | Noticed the sweep's headline number had changed between two runs of the exact same command. Root cause: `now = datetime.now(IST)` shifts each event's exact time-of-day between invocations, which flips peak-window classification for some candidates and cascades into different final numbers - the seeded RNG only controls relative offsets, not the absolute anchor. | Replaced `datetime.now(IST)` with a fixed constant, `_BATCH_ANCHOR_TIME`. Re-ran the harness and full sweep after the fix and updated `docs/RESULTS.md` with the corrected 27-point breakdown rather than leaving the earlier, now-provably-nondeterministic number in place. |

Worth diagnosing *why*, mechanically, instead of stopping at disclosing *that*. Afterward: sensitivity advantage holds at 7/27 grid points, up from 3/27; attempts spent at default params drops slightly (76 to 74); recovered payments unchanged (29) at default params. A mechanically-explained improvement, not a benchmark-tuned one - reordering which offset a failed first attempt falls back to changes which seeded random draw lands where, which can flip specific outcomes, but the reasoning predates the result and the PRD-mandated offsets themselves (24h/72h/7d) were never touched. |
