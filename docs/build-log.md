| 2026-09-14 | A real fail-open bug, found during a deliberate audit of what the classifier and allocator do on malformed input, not by a test failing. `pipeline/allocator.py::allocate()` indexes a ranked candidate list with `attempts_used` (`compliant[attempts_used]`) and computes `attempts_remaining = max(MAX_RETRY_ATTEMPTS - attempts_used, 0)`, neither of which was ever validated against `attempts_used` being negative. `attempts_used=-1` didn't error - it silently reported `attempts_remaining=4` (violating the "never more than 3 attempts" invariant's own bookkeeping) and, via Python's negative-index wraparound, picked the LAST (worst-scored, 168h) candidate instead of the best one - a wrong-but-plausible-looking decision, not a crash. `eval/baseline.py::baseline_decide()` had the identical pattern (`_DAY_OFFSETS_HOURS[attempts_used]`). Separately, `pipeline/ingest.py::FailedPaymentEvent.amount` had no positivity constraint, so a negative amount was silently accepted at Stage 1 despite that module's own docstring claiming "a malformed event fails loudly at the boundary" - a negative amount would have flowed straight into `amount_recovered` arithmetic in the eval harness as a silently-wrong negative figure. | Reproduced directly with a script calling `allocate()` and `ingest()` with `attempts_used=-1` and `amount=-500` before writing any fix, to confirm the bug was real rather than theoretical - confirmed `attempts_remaining=4` and a 168h "chose the worst window" decision, and a negative amount accepted with no error, both with zero exception raised. The existing test suite never covered negative `attempts_used` at all (only values >= the cap, which happened to be accidentally safe due to the `max(..., 0)` clamp - the asymmetry between "too high" and "too low" is exactly what let this hide). | Added an `attempts_within_cap()` guard (the predicate already existed in `pipeline/compliance.py`, already used by `eval/harness.py`'s post-hoc compliance check, but was never called inside the actual decision functions themselves) to the top of both `allocate()` and `baseline_decide()` - fails loudly with `ValueError` instead of producing a wrong decision. Added a Pydantic `Field(gt=0)` on `FailedPaymentEvent.amount` and `Field(ge=0, le=MAX_RETRY_ATTEMPTS)` on `attempts_used`, making the ingestion docstring's existing claim actually true for both fields. Updated `tests/test_allocator.py::test_never_exceeds_attempt_cap_across_causes` - its premise (anything `>= MAX_RETRY_ATTEMPTS` returns `"stop"`) stopped holding for out-of-range-high values, which now raise instead of clamping - split into a boundary test (`attempts_used == MAX_RETRY_ATTEMPTS` still stops) and a new fail-loud regression test for out-of-range values in both directions. Added matching regression tests to `tests/test_baseline.py` and `tests/test_ingest.py`. 16 new tests, 295 passing total, coverage unchanged at 98%. |
