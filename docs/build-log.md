# Build log

Running record of what broke and how it was fixed. Feeds the pitch video's
Failure Recovery narrative, which is graded as its own axis. Add entries as
they happen - do not reconstruct at the end.

| Date | What broke | How it was caught | Fix |
|---|---|---|---|
| 2026-09-03 | `.env` had a malformed/duplicate `LLM_API_KEY` line (missing `=`). A `grep`+`source` attempt to read Razorpay keys for a manual API test echoed key fragments into terminal output before that was caught. | Noticed the malformed-line warning from `python-dotenv` and the leaked fragments in my own command output. | Stopped using shell `source`/`grep` on `.env` entirely; switched to loading credentials only inside Python via `python-dotenv`, never printed. Flagged the leak and the malformed line to the user immediately so the key could be rotated; did not touch `.env` further. |
| 2026-09-03 | S2S UPI AutoPay mandate registration (PRD Sec 5.0 integration tier) is gated off for this Razorpay test account - every `/payments/create/*` route (`create/upi`, `create/recurring`, `create/json`) returns a consistent `400 BAD_REQUEST_ERROR - "The requested URL was not found on the server."`, even for a plain non-recurring UPI collect payment. Customer and order creation both work fine against the same account. | Ran `scripts/capture_fixtures.py` against the live test API, then isolated the failure with three more targeted probes to rule out a wrong-endpoint guess before concluding it was account-level gating; corroborated by an independent published statement that UPI recurring via Collect/Intent "requires requesting activation from the Razorpay Support team." | This exactly matches the feasibility risk PRD Sec 5.0 called out in advance. Did not block on requesting Razorpay Support activation (out of scope for this build window). Kept the real evidence (`data/fixtures/_capture_attempts.json`, including the live customer/order creation and the real 404 error-object shape) and built the 7 cause fixtures from Razorpay's own published error-code docs instead, each labeled `_fixture_source` as documented vs provisional vs live. See `data/fixtures/README.md`. |
| 2026-09-03 | The allocator's candidate scoring (`pipeline/allocator.py`) doesn't depend on `attempts_used` - it's always the same 3 safe-spacing offsets computed from the original failure time. That meant a second retry attempt for the same payment re-selected the identical highest-scoring window the first attempt had already tried and failed at, instead of moving to the next-best one. | The Sec 5.2 sensitivity sweep (`eval/sensitivity.py`) surfaced it, not a unit test: at `funding_event_day=1.5` (an early funding event), the allocator's recovery count was *worse* than the naive fixed-schedule baseline in 9/9 of those grid points - baseline's day1/day2/day3 spread genuinely probes 3 different times, so it was outperforming an allocator that was effectively retrying at the same instant 3 times. | Changed `allocate()` to rank all compliant candidates by score descending and index into the ranking with `attempts_used` (attempt 1 gets the best window, attempt 2 the next-best, etc.) instead of always taking the single top-scored one. Added `test_successive_attempts_pick_distinct_windows_not_the_same_one_again` and `test_attempt_order_follows_descending_score` as regression coverage; re-ran the full batch and sweep after the fix. After the fix, the raw-recovery-count advantage over baseline holds at only 6/27 sweep points (down from the buggy 17/27) - all 6 are exactly `funding_event_day=5.0` (a late funding event baseline's tight day1/2/3 schedule structurally cannot reach, while the allocator's wider PRD-mandated 24h/72h/7d schedule can). Did not re-tune the allocator's offset weights or the safe-spacing offsets to chase a better number - both are PRD-specified (Sec 2's published 24h/72h/7d spacing) or a declared, independently-authored heuristic, and changing either in reaction to a less flattering result is the outcome-model-gaming pattern CLAUDE.md explicitly forbids. Reported honestly in docs/RESULTS.md instead: attempts-spent efficiency and zero-waste-on-unrecoverable-causes hold at every single grid point; raw recovery count only wins when funding timing is late, which is precisely the gap Stage 4 funding-window inference (build step 9) is meant to close. |
